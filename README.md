# «Декларации ДТ» — приложение Битрикс24 (коробка)

Себестоимость техники и других товаров по таможенным декларациям. Сначала сотрудник создаёт декларацию:
ДТ, курс и два процента. Потом заполняет в ней строки — VIN и суммы; стоимость в рублях, утиль сбор с НДС,
«Сумма» и «НДС от маржи» считаются сами. Декларации сворачиваются. Готовые уходят кнопкой «Отправить»:
**каждая строка — отдельный запуск бизнес-процесса** с её значениями.

Устроено как «Перегон техники»: программа лежит на самом портале и работает через его ядро —
**вебхук не нужен**. Кто открыл программу — из сессии портала. Оформление — как у «Перегона».

| Портал | Адрес |
|---|---|
| тестовый (сейчас) | `http://192.168.100.41` |
| боевой (потом) | `https://portal.gkgross.ru` |

## Файлы

| Файл | Что внутри |
|---|---|
| `index.php` | страница программы; с `?action=` — ответы ей (JSON) |
| `install.php` | установка: запоминает владельца, создаёт таблицы, `BX24.installFinish` |
| `lib.php` | вся серверная логика: владелец и доступ, поиск по каталогу, декларации, запуск БП, журнал, «Проверка» |
| `app.js` | интерфейс: новая декларация, таблица с формулами, отправка, доступ, журнал, проверка |
| `style.css` | оформление |

`README.md` на портал класть не нужно.

## Установка (консоль не нужна)

1. **Файлы.** Пять файлов выше — в папку `/local/tools/declarations/` от корня сайта
   (на сервере `/home/bitrix/www/local/tools/declarations/`). Подпапок нет.
2. **Локальное приложение**: Приложения → Разработчикам → Другое → Локальное приложение.

   | Поле | Значение |
   |---|---|
   | Название / пункт меню | Декларации ДТ |
   | «Использует только API» | **снять** — у приложения есть интерфейс |
   | Путь вашего обработчика | `http://192.168.100.41/local/tools/declarations/index.php` |
   | Путь для первоначальной установки | `http://192.168.100.41/local/tools/declarations/install.php` |
   | Права | ничего; если форма без отметки не сохраняется — `user` |
   | Доступно только администраторам | **не включать** — иначе сотрудники с доступом не смогут открыть программу |

3. Открыть приложение **тем администратором, который будет владельцем**. `install.php` запомнит его
   владельцем, создаст таблицы в базе портала и завершит установку — пункт появится в меню.
4. Вкладка **«Проверка»** — всё должно быть зелёным. Там же пробный поиск по VIN и **ID шаблона БП** (см. ниже).
5. Вкладка **«Доступ»** — выдать доступ сотрудникам.

При установке браузеру нужен доступ к `api.bitrix24.com` (скрипт `BX24`), как у «Перегона».

## Перенос на боевой портал

Те же пять файлов — в `/local/tools/declarations/` боевого. Там своё локальное приложение
с адресами `https://portal.gkgross.ru/local/tools/declarations/index.php` и `…/install.php`.
Открыть его будущим владельцем → «Проверка» → «Доступ». Владелец, доступы, настройки и данные у каждого портала свои:
на боевом заново указать ID шаблона БП и, если отличаются, коды полей «Резерв» и «Орган въезда/выезда».
XML_ID значений списков на боевом свои — программа берёт их из шаблона сама, вписывать не нужно.

## Обновление

Заменить файлы — данные не теряются: владелец, доступы и настройки хранятся в настройках портала
(`b_option`, модуль `gross.declarations`), декларации и журнал — в таблицах базы. Адреса скриптов
и стилей несут метку времени файла — браузер возьмёт новые сам. Старые черновики, где курс стоял в каждой строке,
открываются с курсом первой строки.

## Доступ

| Кто | Что может |
|---|---|
| Владелец — администратор, который установил программу | всё, плюс вкладки «Доступ», «Журнал действий», «Проверка» |
| Сотрудник, которому владелец выдал доступ | вкладка «Декларации», в том числе «Отправить». Прав на каталог и на шаблон БП не нужно |
| Остальные, **включая других администраторов портала** | экран «нет доступа» |

* Владелец один. Если его уволят или удалят, владельцем станет первый администратор портала, открывший программу.
* Доступ проверяется на каждом запросе: снятый сотрудник теряет его сразу, без перезагрузки страницы.

## Где хранятся данные

| Что | Где |
|---|---|
| Владелец, список доступа, настройки (поиск, шаблон БП, поля «Резерв» и «Орган въезда/выезда») | `b_option`, модуль `gross.declarations` |
| Декларации | таблица `gross_dt_decl`: одна строка — одна декларация (ДТ уникальна), курс, проценты и строки — JSON в `data` |
| Журнал действий | таблица `gross_dt_log` |

Таблицы создаются сами при установке или первом открытии программы. Поддерживаются MySQL/MariaDB и PostgreSQL.
Декларации общие: их видят и правят все, у кого есть доступ. Черновик сохраняется сам через полсекунды после правки.

## Как работает интерфейс

1. **Новая декларация** (верхний блок) — четыре ячейки: **ДТ**, **Курс по ДТ**, **Утиль сбор с НДС, %** (по умолчанию 22)
   и **НДС от маржи, %** (2,64). «Загрузить данные» — появляется декларация с этими значениями и с одной пустой
   строкой: курсор сразу в её VIN.
   * В поле **ДТ** с 3 цифр появляется список **уже существующих деклараций**: отправленные из программы и ДТ из
     свойства «Декларация» товаров (потом источником отправленных станет список портала — меняется только класс
     `Archive` в `lib.php`). Выбрали из списка —
     курс и проценты подставятся, кнопка станет «Открыть декларацию»: декларация вернётся в работу **со всеми строками,
     как была** (VIN, марка, резерв, суммы, ручные значения), её можно править и отправить снова.
     Номер набран целиком без выбора — такая декларация подхватится сама. Декларация, которая уже в работе, в списке
     помечена «уже в работе» — выбор просто показывает её.
   * **Уже в работе** — выбрали из подсказки или набрали номер и нажали «Открыть декларацию»: она раскрывается в списке.
   * **Есть в Битриксе** — у товаров заполнено свойство «Декларация» (`DECLARACIA`) этим номером. Выбрали из подсказки
     (или набрали номер и «Открыть декларацию») — **открывается**: строка на каждый её VIN, товар и «Марка модель»
     подбираются. Эти VIN уже были в декларации — подсвечены и повторно не уйдут; новые VIN добавляются и отправляются
     (строки с бывшими VIN перед отправкой убрать). Из XML такую ДТ тоже можно загрузить.
   * Нет в списке — «Загрузить данные», всё как раньше.
2. **Строки** заполняются прямо в таблице декларации — все колонки, как раньше. Слева от строки: **«+»** — пустая строка
   ниже, **«копировать»** — копия строки ниже. Справа «×» — удалить, с кнопкой «Вернуть». Внизу — «+ Строка».
3. **Курс и проценты** стоят в заголовках колонок «Курс по ДТ», «Утиль сбор с НДС» и «НДС от маржи» и меняются там же —
   пересчитывается вся декларация.
4. **Ячейки «авто»** (Стоимость в рублях, Утиль сбор с НДС, Сумма, НДС от маржи) считаются сами, но их **можно
   переписать вручную**: вписанное значение заменяет формулу, ячейка становится жёлтой, и следующие формулы считаются
   уже от него (как перезаписанная ячейка в Excel). Кнопка **↺** в ячейке или пустое значение — снова формула.
5. **«Отправить»** — окно со списком готовых деклараций, можно снять галочки, дальше — бизнес-процесс (см. ниже).
   **Если хоть в одной декларации есть ошибка, не отправляется ничего:** кнопка красная, по нажатию — окно со всеми
   ошибками по декларациям и строкам, ячейки подсвечиваются, «Показать ошибку» ведёт к первой. Исправили — отправка как обычно.

* **ДТ** — только цифры и дроби «/», дробей сколько угодно (между ними — цифры). Буквы и другие знаки в поле не вводятся. Средняя часть читается как дата: «100326» → от 10.03.2026.
  Такая ДТ уже есть — программа не создаёт вторую, а раскрывает существующую.
* **Курс по ДТ** — ровно 4 знака после запятой. Неверный курс подсвечивается над таблицей декларации.
* **Повторный VIN** — ошибка (по всем декларациям).
* **VIN уже был в декларации** — у товара заполнено свойство **`DECLARACIA`** (код меняется в «Проверке»):
  ячейка VIN сразу красная — «Уже был в декларации …». Проверяется при вводе VIN (набрали 17 знаков, выбрали из
  подсказки или ушли из ячейки), в подсказках такой товар помечен, при загрузке XML — сообщение. Строку не отправить,
  а значит, по правилу выше, не уходит ничего. Сервер проверяет свойство ещё раз перед запуском БП (и для строк, где
  товар не выбран, — ищет его по VIN). Та же ДТ отправляется снова, но уже бывшие VIN — нет: их строки надо убрать (так задумано).
* **«Загрузить XML»** (рядом с «Очистить») — новая декларация из XML-файла ДТ, см. ниже.

## Загрузка XML

Принимается **только XML** выгрузки декларации на товары (`ED_Container` → `ESADout_CU`, тот же файл, что открывается
в Excel). Файл с другим расширением, XML без `ESADout_CU` или битый XML — отказ с понятным сообщением. Кодировка —
из заголовка файла (UTF-8 и windows-1251). Префиксы тегов в файлах бывают разные (`cat_ru:`, `catESAD_cu:`, `ns6:`…),
поэтому теги ищутся по имени без префикса.

После выбора файла открывается окно: что взято из декларации, номер ДТ можно поправить. «Загрузить данные» — и
она в списке, строки заполнены. Остальные колонки (контракт, даты, «Отправка в Китай», расходы) — вручную, как раньше.
Курс берётся из XML, проценты — из блока «Новая декларация» (обычно 22 и 2,64).

| Что | Графа ДТ | Тег в XML | Куда |
|---|---|---|---|
| Номер ДТ | A | **комментарий в конце файла** `</ED_Container><!--ND=10009100/131026/5166277-->` (`Local=…` — местный номер, не берётся); нет — `CustomsCode / RegistrationDate / GTDNumber` вне представленных документов; нет и их — из имени файла `10009100_131026_5166277.xml` → `10009100/131026/5166277` | название декларации |
| Курс | 23 | `ESADout_CUMainContractTerms/ContractCurrencyRate` | «Курс по ДТ», до 4 знаков |
| Орган въезда/выезда | 29 | **по коду поста** `BorderCustomsOffice/Code` (10719110 → `10719110 Т/П "МАПП ЗАБАЙКАЛЬСК"`); нет в списке — по названию `OfficeName`, потом `DeliveryPlace` | «Орган въезда/выезда», ID значения; нет в списке или список не задан — текст из XML, ячейка открыта для ручного ввода |
| Резерв | 30 / 29 / 20 | **по коду таможни, где товары**, `GoodsLocation/CustomsOffice` (10504080 → `10504080, Г.ЧЕЛЯБИНСК`), или коду из номера ДТ; нет в списке — по названию: `OfficeName` / `DeliveryPlace` («Т/П МАПП ЗАБАЙКАЛЬСК» → `10719110, ЗАБАЙКАЛЬСКИЙ КРАЙ`), потом город склада (графа 30) | «Резерв (где растоможили)», ID значения; не подобрался — ячейка открыта для ручного ввода (пустая) |
| Сборы, Пошлина, НДС | 47 | `PaymentAmount` по `PaymentModeCode`: 1… — сборы, 2… — пошлина, 5… — НДС; нет графы 47 — итоги графы B | **поровну на все VIN**: 9 000 000 и 3 VIN → по 3 000 000 в строку; копейки от деления — в первые строки, сумма сходится с ДТ |
| Строки | 31.1 | `GoodsAutomobile/VINID`; вместо VIN «ОТСУТСТВУЕТ» — `ChassisID` (№ шасси) | **1 VIN — 1 строка**; товар ищется в каталоге по VIN, как при вводе руками — встаёт «Марка модель» |

Что не перенеслось, видно в окне жёлтым: платежи других видов (например, акциз), отсутствующие в XML графы,
расхождение мест для резерва.

**Резерв и орган — всегда списки.** Вписать своё можно только там, где при загрузке XML значение **не подобралось**
из списка: такая ячейка жёлтая, в ней поле с подсказками из списка. Вписали название из списка — хранится и уходит
ID значения (так же — «челябинск» или код таможни «10504080»). Своего значения нет в списке параметра шаблона —
отправка остановится с ошибкой: параметр-список БП текст не принимает. В остальных строках — обычный выпадающий список.
Такая ДТ уже в работе или уже отправлялась — вторая не создаётся. Загрузка и создание пишутся в журнал.

## Колонки и формулы

Порядок — как в листе «Себестоимость после 01.26» таблицы `Кириллу (1) (1).xlsx`. ДТ — в названии декларации.
Колонки «управление» в программе нет — убрана по просьбе заказчика.

| Колонка | Ввод |
|---|---|
| VIN | с подсказками из **всех товаров каталога** (не только техники), от 3 знаков VIN или названия |
| Марка модель | **из товара:** свойство «Модификация» (`MODIFIKATSIYA`). Встаёт при выборе VIN из подсказки и при вводе VIN вручную (если он нашёлся в каталоге), **стирается, когда VIN стёрли или изменили**. Руками не правится. Товар найден, а «Модификация» у него пустая — в ячейке «не заполнена в товаре». При каждом открытии программы берётся свежей из каталога |
| Контракт | текст |
| Резерв (где растоможили) | **выпадающий список** — значения поля `UF_CRM_14_1793082775`: 2494 «10504080, Г.ЧЕЛЯБИНСК», 2495 «10719110, ЗАБАЙКАЛЬСКИЙ КРАЙ». В строке хранится ID значения |
| Орган въезда/выезда | **выпадающий список** — значения поля `UF_CRM_14_1793183988` (меняется во вкладке «Проверка»): 2496 «39857301 Т/П "Бахты"», 2497 «10719110 Т/П "МАПП ЗАБАЙКАЛЬСК"». В строке хранится ID значения. Графа 29 ДТ |
| Дата выезда с границы, Дата прибытия на пост | дата |
| Отправка в Китай $Y | число, обязательно |
| Курс по ДТ **[11,4368]** | **курс декларации** — задаётся при создании, меняется в заголовке колонки |
| Стоимость в рублях | **авто:** `Отправка × Курс` (все «авто» можно переписать вручную, ↺ — вернуть формулу) |
| Доставка до таможни, Сборы, Пошлина, НДС, Утиль сбор | число |
| Утиль сбор с НДС **[22] %** | **авто, как в Excel** (`=(P2*22%)+P2`): `(Утиль сбор × %) + Утиль сбор` |
| Брокерские, СВХ, Стоянка | число |
| **Доп. расходы:** ЖД в России · ПТС ПСМ быстрота · Доп. расходы с погрузкой/выгрузкой | число, общая шапка над тремя колонками |
| Сумма | **авто, как в Excel** (`=K+L+M+N+O+Q+R+S+T+U`): Стоимость + Доставка + Сборы + Пошлина + НДС + Утиль с НДС + Брокерские + СВХ + Стоянка + ЖД в России |
| НДС от маржи **[2,64] %** | **авто:** `Сумма × % + Сумма` |

* «ПТС ПСМ быстрота» и «Доп. расходы с погрузкой/выгрузкой» в «Сумму» **не входят** — как в Excel.
  Чтобы включить: в `app.js` поставить `inSum: true` у `pts` и `loading`, в `lib.php` добавить их в `Formula::SUM`.
* Колонки описаны одним списком `FIELDS` в `app.js` (таблицы строятся по нему) и `Formula` в `lib.php`.

## Отправка в бизнес-процесс

Как в «Перегоне»: **программа не создаёт элементы CRM, а только «толкает» БП** — запускает шаблон с входными
параметрами. Одна строка декларации — один запуск. Что делать со значениями (создать элемент смарт-процесса и т. п.) —
решает сам БП.

**Настройка** — вкладка «Проверка» → блок «Отправка в бизнес-процесс»:

1. Создать шаблон БП в смарт-процессе, где лежат поля «Резерв» и «Орган въезда/выезда» (`UF_CRM_14_…`), с параметрами
   из таблицы ниже — **коды точно такие же**. Обязательные параметры шаблона, которых нет в таблице, должны иметь
   значение по умолчанию.
2. В блоке **«Создать элемент»** шаблона в каждое поле элемента поставить его параметр: поле → «…» → «Параметры
   шаблона» → нужный параметр (в поле встанет `{=Template:КОД}`). Списки — строго в свои поля:

   | Поле элемента | Параметр |
   |---|---|
   | `UF_CRM_14_1793082775` «Резерв (где растоможили)» | `RASTOMOZHENO` |
   | `UF_CRM_14_1793183988` «Орган въезда» (значения «Бахты», «МАПП ЗАБАЙКАЛЬСК») | `ORGAN_VEZDA_VIEZDA` |

   Сохранить блок, потом шаблон — кнопкой «Сохранить» внизу шаблона. Без неё изменения не запишутся.
3. Вписать **ID шаблона** и нажать «Сохранить». «Проверка» покажет, каких параметров в шаблоне не хватает, а в таблице параметров
   блока «Отправка в бизнес-процесс», в колонке «Что передаётся», под каждым параметром-списком — плашки проверки (см. ниже). Всё зелёное — можно отправлять.

«Множественный» получает значение одним элементом списка.

**Резерв и орган в БП.** У параметра «Привязка к спискам документа» значения — это значения поля-списка,
как их видит БП: в CRM ключ значения — его **XML_ID** (внешний код), а не ID. ID 2494 туда не встаёт, поле в БП
остаётся пустым. Поэтому при запуске программа берёт список того поля, к которому привязан параметр, и переводит
значение строки в его ключ: сначала ищет ID, потом XML_ID, потом название. Значения нет в списке параметра —
отправка не начинается, в ошибке видно, какой строки и какого значения это касается. Список параметра не прочитался —
уходит XML_ID значения поля. Параметр с типом «Список» тоже работает: значение сверяется с его вариантами.

**Плашки проверки** — в «Проверке», блок «Отправка в бизнес-процесс», колонка «Что передаётся», под `RASTOMOZHENO` и `ORGAN_VEZDA_VIEZDA`
(и в отчёте выше). Программа читает **сохранённый** шаблон и показывает:

| Плашка | Что значит |
|---|---|
| ✓ «блок «Создать элемент»: поле … = {=Template:…}» | поле элемента берётся из параметра — всё верно |
| ✓ «В БП уходит: … → «c31b927c…»» | какой ключ уйдёт за каждое значение колонки |
| ✕ «поле … НЕ берётся из этого параметра» | в блоке «Создать элемент» поле элемента пустое или в нём другое. Видно, когда шаблон сохранён, и **где параметр стоит на самом деле** («Параметр стоит в другом месте: … `DynamicEntitiesFields.1056_UF_CRM_…`») или что он нигде не стоит (шаблон не сохранён или правился другой) |
| ✕ «параметр привязан к полю …, а должен — к …» | в настройках параметра выбрано не то поле-список |
| ✕ «в его списке нет: …» | значения колонки нет в списке параметра — с ним отправка остановится |
| ! жёлтая | блока «Создать элемент» нет (или их несколько), параметр не список, список не прочитался |

**Поле в элементе пустое, хотя в «Проверке» ключи зелёные** — значит, программа отправляет верно, а БП не пишет
значение в поле. Чаще всего в смарт-процессе два похожих поля («Орган…»), и параметр поставлен не в то: красная
плашка покажет, в какое. Убрать его оттуда и поставить в поле из таблицы выше, сохранить шаблон, обновить «Проверку».
При отправке то же предупреждение приходит в сообщении «Отправлено: N. Бизнес-процесс запущен, но — …»:
БП запускается, но поле в элементе останется пустым.

**Как идёт отправка:**

* Сервер проверяет **сохранённую** декларацию (не то, что прислал браузер): ДТ, курс, строки, повторы VIN, списки
  «Резерв» и «Орган въезда/выезда», что товары ещё есть в каталоге и VIN не был в декларации (`DECLARACIA`), что в шаблоне
  есть все параметры и значения списков есть в списках параметров. Ошибка — не запускается **ни одна** строка.
* Отправленная декларация **из приложения убирается**: её нет в списке, поиске, счётчиках, и её VIN больше не считаются
  повтором. Найти её можно только набрав номер ДТ в «Новой декларации». Открыли и отправили снова — каждая строка
  уходит в БП ещё раз. Журнал действий (у владельца) по-прежнему пишет, кто и когда отправлял.
* Дальше декларация закрывается для правок и строки запускаются по очереди. Каждый запуск запоминается сразу —
  повторное «Отправить» (например, после обрыва связи) **не запустит строку второй раз**.
* Длинная декларация уходит порциями: страница повторяет запрос, пока не уйдут все строки, и показывает «ушло N из M».
* Если запуск строки сорвался, декларация остаётся «Отправлено N из M»: правки закрыты, «Отправить» продолжит
  с оставшихся строк.
* Инициатор БП — сотрудник, нажавший «Отправить». Если в шаблоне ровно один блок «Создать элемент» этого
  смарт-процесса, после него БП переключается на созданный элемент (как в «Перегоне»). Ошибки из журнала БП
  программа показывает после отправки.
* Двое не отправят одну декларацию одновременно — второй получит «дождитесь окончания».

## Поиск по VIN

Ищутся **все товары**: каждый каталог товаров портала (инфоблоки торговых предложений пропускаются),
все папки, только активные товары. Совпадение — по VIN, названию, модели и артикулу. Поля подбираются сами:

* VIN — строковые свойства со словами «VIN», «серийный», «заводской номер»;
* модель — свойства «модель» / «марка»: по ним тоже ищется товар;
* «Марка модель» строки — свойство с кодом `MODIFIKATSIYA` (код меняется в «Проверке»; нет такого кода — берётся
  свойство с названием «Модификация…»), видна и в подсказке. «Проверка» показывает, у скольких товаров она заполнена;
* VIN, набранный вручную, ищется точно — в том числе среди нескольких VIN в карточке («4583/X89777222R0EV8014»);
* у товара без VIN (навесное, запчасти) в ячейку VIN встаёт его название.

Если подобралось не то — вкладка «Проверка» → «Настройки поиска»: ID инфоблоков и поля (`PROPERTY_<ID>`).

## Журнал действий

Пишется каждое действие: вход и выход, вкладки, поля новой декларации, создание декларации, «Загрузить XML»,
каждое изменение ячейки (было → стало), выбор из подсказки, подстановка и стирание «Марки модели», добавление,
«+», копирование, удаление и возврат строки, смена курса и процентов, правка ДТ, удаление декларации,
свернуть/развернуть, поиск, неудачные попытки создать декларацию, отправка в БП и её отмена,
выдача и снятие доступа, проверка и настройки, выгрузка журнала.

Записи уходят на сервер пачками, при закрытии страницы — через `sendBeacon`. Сотрудника, время и IP ставит сервер
по сессии портала. У записи свой `id` — повтор после обрыва связи дубля не даёт. Владелец смотрит журнал во вкладке
«Журнал действий»: фильтры по сотруднику и виду действия, поиск, «Скачать CSV» (последние 5000 записей).

POST, тело JSON с `sessid`; ответ `{ok: true, data}` или `{ok: false, error}`.
